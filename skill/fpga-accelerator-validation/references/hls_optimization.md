# 用证据选择 HLS 优化

## 建立可归因的目标

先从逐阶段计时选择瓶颈，再读取该阶段的循环调度、带宽、存储端口、扇出和布线路径。把“需要更快”落实为当前耗时与目标，同时写出限制：数值契约、时钟、资源、接口、权重或并行度中哪些可改变。

| 现象 | 优先检查 | 可能采取的改变 | 复核代价 |
|---|---|---|---|
| 乘加循环 II 大于目标 | 循环相关、BRAM 端口、累加反馈 | pipeline、分银行、局部归约 | 顺序变化造成的溢出/舍入差异 |
| DSP 闲置但吞吐低 | 输入/权重加载、后处理占比、AXI 停顿 | burst、片上复用、producer/consumer 重叠 | FIFO 背压与死锁 |
| PE 增加但整网几乎不提速 | 通道尾组、补齐、memory/后处理瓶颈 | 优先修复非计算开销，或调整并行划分 | 更多 BRAM/LUT、尾通道正确性 |
| 综合估计好但实现不满足时序 | 宽 mux、地址计算、控制扇出、长跨区连接 | 地址通路缩位、流水线、局部控制复制 | latency、复位和握手变化 |
| 浅宽 FIFO 大量吃 BRAM | HLS 存储绑定、端口与深度 | 根据宽度/深度尝试 LUTRAM 或调整流水级 | LUT/FF 与新布局时序 |
| 提频后实测不变 | 真实时钟、计时范围、DDR 与软件占比 | 读回时钟配置，分离核与端到端时间 | 主机传输可能成为主瓶颈 |

这些是诊断分支，不是固定 pragma 配方。不要在没有循环证据的情况下统一添加 `UNROLL`、`ARRAY_PARTITION complete` 或超深 FIFO。

## 设计一轮改变

写一段可检验的假设，例如：“输出重定标占每行时间约三分之一，分成独立消费者可能与下一行乘加重叠；保持数值、PE、时钟不变。”记录预计增加的缓冲、控制和资源。

如果改变会影响位宽、算子顺序或量化，先明确这是算法/数值变更；不能继续沿用原参考输出声称等价优化。用户要求保持模型与量化时，应另选优化方法。

## DATAFLOW 与接口

明确每个状态、FIFO 和缓冲的唯一读写归属。检查任务是否等待对方产生自己才能产生的数据，或在函数返回前不排空流。合理的 C 仿真 stream 最大深度不等于 RTL 固定深度足够；用有背压的 C/RTL 情景判断。

区分边界地址与内部索引位宽，避免为了省资源把外部物理地址截断。总线宽度改变还需同步检查打包、对齐、burst、驱动长度和 PS cache 操作。

## 每轮接受标准

1. 所选数值与接口回归通过，参考没有被悄悄重建为候选输出。
2. 与改动相关的综合/C/RTL、产物身份与布线检查通过，或明确尚缺哪一阶段。
3. 有实际板测时才给板上收益；比较输入、精度、计时范围、cache 与重复方式一致。
4. 同时给 LUT/FF/BRAM/DSP、时钟和各阶段变化；允许“资源增加但无实际收益”的候选被放弃。

保留测量记录与最后可用版本的标识。是否在交付目录保留历史工程由用户决定；要求只交付最新版时，删除旧工程树，保留解释当前结论所必需的测量证据即可。
